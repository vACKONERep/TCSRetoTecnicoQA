================================================================================
CONCLUSIONES — Ejercicio 2, APIs Signup y Login de DemoBlaze
Karate 1.5.1
================================================================================

Que probe
Los dos servicios que pide el enunciado, ambos con POST y JSON:

  POST https://api.demoblaze.com/signup
  POST https://api.demoblaze.com/login

Casos, todos dentro de Scenario Outline (no hay un escenario copiado por caso):

  SU-01  Crear un usuario nuevo                         signup-cases.csv
  SU-02  Volver a crear ese mismo usuario               signup-cases.csv
  LG-01  Login con usuario y password correctos         login-cases.json
  LG-02  Login con password incorrecto                  login-cases.json
  LG-03  Login con un usuario que no existe             login-cases.json

LG-03 no lo pedia el enunciado al pie de la letra (pide "usuario y password
incorrecto"). Lo deje porque un password malo y un usuario que no existe
devuelven mensajes distintos, y los dos son un login incorrecto. El de
password malo ya cubre el caso pedido.

De donde salen los datos
- La forma de cada caso esta en CSV (signup) y JSON (login).
- Los textos esperados no se repiten en esos archivos. La columna expectedKey
  apunta a la variable messages de karate-config.js.
- baseUrl y defaultPassword tambien salen de karate-config.js.
- El username se genera en cada ejemplo (timestamp + random). La API no tiene
  un servicio para borrar usuarios, asi que un nombre fijo fallaria en la
  segunda corrida.

Resultado de la ejecucion (21 de septiembre de 2026)
Comando, desde la raiz: .\mvnw.cmd -f karate-api\pom.xml clean test
JDK 17. Karate 1.5.1.

  Signup: 2 escenarios, 0 fallos.
  Login:  3 escenarios, 0 fallos.
  scenariosfailed: 0.
  Reporte: target/karate-reports/karate-summary.html
  Ahi queda, por escenario, el request (entrada) y el response (salida).

Que observe de la API
1. Signup y Login responden HTTP 200 tambien cuando el negocio falla.
   Mirar solo el status no distingue exito de error. El test afirma 200
   y, encima, el cuerpo.
2. Los mensajes reales, que deje en messages, son estos:
     usuario repetido     "This user already exist."
     password malo        "Wrong password."
     usuario inexistente  "User does not exist."
   El primero esta mal escrito (falta la "s" de "exists"). El test usa el
   texto que devuelve la API, no el que seria correcto en ingles. Si algun
   dia lo corrigen, se cambia una linea de karate-config.js.
3. El signup correcto no devuelve un usuario ni un id. El cuerpo viene vacio,
   sin errorMessage. Eso es lo que tomo como alta exitosa.
4. El login correcto no devuelve JSON. Devuelve un texto:
     Auth_token: <valor>
   El login fallido si devuelve JSON con errorMessage. El outline tiene que
   bifurcar: token si el caso es valid, errorMessage en los otros dos.
5. Esos dos recursos, en el uso real de la pagina, solo se llaman con POST.
   No sume GET, PUT ni DELETE: no forman parte del flujo de registro y el
   enunciado no los pide. Probar un metodo que el sitio no usa solo habria
   agregado un caso rojo o ambiguo.
6. Karate 1.5.1 es la linea que corre en JDK 17. Karate 2 pide JDK 21.
   Me quede en 1.5.1 para no subir el requisito del readme.

Riesgos
- La API es publica y no aisla datos. Dos corridas al mismo tiempo con el
  mismo username podrian pisarse. El stamp por ejemplo lo hace muy poco
  probable, no imposible.
- No hay ambiente aparte de produccion del demo. No existe un karate.env
  con otra URL porque el sitio no publica una.

Que mejoraria
- Medir el tiempo de respuesta. Hoy no hay un umbral; el demo a veces tarda
  y un limite inventado fallaria sin decir nada del contrato.
- Si mas adelante hubiera un endpoint de carrito, encadenar el Auth_token
  que ya captura el login.

Criterios del correo, en una linea
1. Corren los casos de signup y de login, que son los metodos POST de esos
   dos servicios. 5/5 en la corrida del 21 de septiembre de 2026.
2. Informe karate-reports generado.
3. Features con variables (baseUrl, password, messages, username generado).
4. Scenario Outline: signup-cases.csv y login-cases.json.
